# Приёмка поведения

`make check` — воспроизводимый технический минимум. Он не запускает браузер и не подтверждает deployment. Для короткого цикла использовать соответствующий `check-api`, `check-web` или `check-harness`.

## Изоляция

Использовать отдельную временную SQLite-базу через `DB_PATH` и свободный локальный порт через `PORT`. Настройки читать в `apps/api/internal/config/config.go`. Не выполнять destructive smoke checks на пользовательской базе. Временный сервер завершить после проверки; сохранить только нужные evidence в `.harness/`.

## URL shortener: выбирать затронутые сценарии

1. Создать корректную HTTP(S) ссылку; проверить ответ и появление в списке.
2. Открыть `/s/{code}` без автоматического следования redirect; проверить HTTP 302 и `Location`.
3. Для изменений click tracking проверить eventual increment с ограниченным ожиданием, а не предположением о мгновенной записи.
4. Повторить custom slug: ожидается конфликт. Проверить запрещённую схему URL и невалидный slug.
5. Выключить тестовую ссылку, проверить недоступность redirect; включить обратно.
6. Проверить поиск, empty state, ошибку сети; удалить только созданную тестовую ссылку.

## UI

На затронутом экране проверить loading/empty/error/success, keyboard navigation и focus, узкую ширину около 375 px и desktop. Если меняются theme-sensitive стили — обе темы. QR/clipboard/download проверять только когда затронуты. Зафиксировать конкретные действия и результат; скриншот дополняет, но не заменяет проверку взаимодействий.

Если инструменты браузера недоступны, оставить точный ручной сценарий и назвать его непроверенным. Нельзя писать «все тесты прошли», если выполнились только сборка и lint.
